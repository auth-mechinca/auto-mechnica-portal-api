# Demo Scope: Auto-Parts Business System
**Working functional prototype** — real backend + database, not a clickable-only mockup.
Prepared for wireframing handoff (Claude Design) → implementation.

---

## 0. Purpose & Audience

This document scopes a **client demo** covering five areas the client asked to see:

1. POS (Point of Sale)
2. IMS (Inventory Management)
3. Financial Core
4. RBAC (Role-Based Access Control)
5. Backoffice, including Purchase Orders, Price Management, and Supplier management

Because this is a **functional prototype** (confirmed), every screen below needs a real page, a real API call, and a real database write — not placeholder data. Scope has been kept intentionally tight so this is buildable as a demo, not the full Phase 1-2 production system. See **Section 8: Out of Scope** for what's deliberately excluded.

## 1. Tech Stack (for context — informs what Claude Design should design for)

| Layer | Choice | Notes |
|---|---|---|
| Backend | Node.js + Express | Structure the codebase by module (pos/, ims/, financial/, backoffice/, auth/) from day one |
| Database | PostgreSQL, self-hosted | No managed DB service |
| ORM | Drizzle (recommended) or Prisma | Drizzle preferred if backend ends up running through a connection pooler |
| Auth | Session or JWT-based, role claim embedded in token/session | RBAC checks happen server-side on every request, not just hidden in the UI |
| Frontend (web) | **React**, via **Next.js** | Next.js pairs directly with the Vercel deployment plan; React over Angular for faster iteration with a small team and a much shorter path to a mobile app (below) |
| Frontend (future mobile — out of scope for this demo) | **React Native (via Expo)** | Not Angular/Ionic and not fully native (Swift/Kotlin) — React Native shares the same language, most business logic, and the API client with the Next.js web app, so the mobile app isn't a second codebase written from scratch. Confirmed out of scope for the demo itself. |
| Deployment | **API: persistent Node process on the same host as Postgres. Frontend: Next.js on Vercel.** | **[CONFIRMED]** The serverless option was dropped: Vercel functions against self-hosted Postgres would have required PgBouncer plus a pool size of 1, and put a Ghana → Europe round trip on every POS query. Cold starts were also a real risk to how responsive the demo feels in front of the client. Vercel now hosts the frontend only. |

> **Build note for the demo itself:** even though mobile is out of scope here, keep API calls and state logic in plain, framework-agnostic modules — not buried inside React components. Costs almost nothing to do now, and it's the difference between React Native being a genuine head start later versus another rewrite.

### 1.1 Repository layout

Three repositories, under the `auth-mechinca` GitHub org:

| Repo | Contains |
|---|---|
| `auto-mechnica-portal-api` | These documents (`docs/`), the Express API, **the schema** (Drizzle TS schema → `drizzle-kit generate` → SQL migrations committed under `drizzle/`), the **demo seeds** in `seeds/`, and the local database bootstrap in `docker/`. |
| `auto-mechnica-erp-ui` | Next.js frontend |
| `migration-scripts` | **Tally data migration** only — export → clean → transform → load, run once at cutover. Deliberately *not* a mirror of the schema migrations. |

Schema migrations are generated by Drizzle and live only in the API repo — they are never hand-edited and never copied elsewhere by hand. Seeds are kept in a separate `seeds/` directory rather than among the migrations, because migrations run once and are immutable while seeds are idempotent and re-runnable.

**Revised 17 September:** seeds were originally assigned to `migration-scripts`. They moved to the API repo for three reasons that only became clear once the API existed: the four demo accounts must be hashed with the app's own `hashPassword` and `BCRYPT_COST`, and a cost that drifts between seed and app silently reopens a login timing leak; seed rows are typed against the Drizzle schema, so a renamed column breaks them at compile time instead of silently at run time; and `npm run db:setup` is an API-repo script, so reaching into a sibling repo would assume a fixed relative path between two independently cloned checkouts. The Tally migration stays in `migration-scripts` — it is a genuinely separate one-off job with its own dependencies and no business in the API image.

All database objects are created in a named **`app`** schema, never `public`, and the app's runtime database role has no DDL rights — migrations run as a separate privileged user. The database bootstrap (roles, grants, revoking `public`) lives in the API repo under `docker/`, because it has to run inside the Postgres container as part of `db:setup`.

## 2. Roles for the Demo (RBAC)

**Confirmed: the demo will show logging in as multiple distinct role accounts**, not one account with permissions explained. Four roles cover all five requested demo areas:

| Role | Demo login | Can access | Cannot access |
|---|---|---|---|
| **Sales (POS)** | `sales@demo` | POS screen only — search, sell, take payment | Backoffice, inventory editing, purchase orders, pricing, financial reports, supplier data |
| **Purchasing Officer** | `purchasing@demo` | Backoffice: Suppliers, Purchase Orders, Price Management, Inventory (view + adjust) | User management, financial reports/payments, system settings |
| **Accountant** | `accounts@demo` | Financial Core: receivables, payments, cheques, MoMo, customer balances | Purchase orders, price management, user management |
| **Owner/Admin** | `admin@demo` | Everything, including user/role management | — (full access) |

**Demo narrative:** log in as each role in turn, show the UI visibly changing (not just greyed-out buttons — different roles should see a genuinely different navigation/menu), attempt one blocked action per restricted role to make the boundary tangible (e.g., Sales account cannot reach `/backoffice/*` routes even by URL).

## 3. Module: POS (Point of Sale)

**Role:** Sales only.

### Screens
- **POS Home / Sale Screen** — part search (by name, part number, or vehicle fitment), add to cart, quantity, view line total
- **Cart / Checkout** — cart summary, select payment method (Cash / Cheque / MoMo), enter payment details, complete sale
- **Sale Confirmation** — receipt-style summary, option to start a new sale

### Key behaviors
- Prices shown are **read-only**, pulled from the price set in Backoffice → Price Management (Section 6). Sales staff cannot override price.
- Stock availability shown per part; selling reduces stock in real time (writes a Stock Movement record, reduces Inventory Balance).
- Completing a sale creates a Sales Invoice and, if payment method is Cheque or MoMo, feeds into Financial Core (Section 5).

---

## 4. Module: IMS (Inventory Management)

**Role:** Purchasing Officer, Admin (view/edit); Sales (view stock availability only, inside POS).

### Screens
- **Product/Part List** — searchable table: SKU, name, brand, category, current stock, sell price
- **Product Detail / Edit** — part number, OEM number, brand, category, vehicle fitment (Year/Make/Model/Engine — simple multi-entry field for the demo, not a full cross-reference database), current stock
- **Stock Adjustment** — manual adjustment with a required reason (damage, loss, count correction)
- **Low Stock View** — simple list of parts below their configured reorder point

### Key behaviors
- Receiving stock happens through Purchase Orders (Section 6), not directly here, to keep the demo's data flow honest to the real system.
- **[CONFIRMED]** **Single location for the demo, location-aware schema.** No location selector appears on any screen and no stock-transfer workflow is built — but `location_id` is present from day one on Inventory Balance and Stock Movement, defaulting to a single seeded `Main Shop` row.

  The reason for the split: adding multi-location later is then UI work plus a transfer workflow, rather than a migration that has to backfill a location onto every historical balance and movement record in a live financial system. The dropdown is the cheap part; the backfill is not.

## 5. Module: Financial Core

**Role:** Accountant, Admin.

### Screens
- **Customer Accounts List** — customer name, running balance, ageing (current/30/60/90+)
- **Customer Account Detail** — invoice history, payment history, current balance
- **Record Payment** — select customer, select invoice(s) to allocate against (or "pay against account"), select method:
  - **Cash** — clears balance immediately
  - **Cheque** — recorded as *pending*; separate action to mark *cleared* or *bounced* (balance only updates on clearing)
  - **MoMo** — network (MTN/Telecel/AirtelTigo), transaction ID, phone number; clears immediately
- **Cheque Status Queue** — list of pending cheques, action to mark cleared/bounced

### Key behaviors
- Balance is always **derived** (sum of invoices minus cleared/allocated payments) — never a directly-editable field, even for Admin. This is a hard rule carried over from the discovery phase, not a nice-to-have.
- A bounced cheque reverses the balance and is visibly flagged in history — never silently deleted.

## 6. Module: Backoffice — Suppliers, Purchase Orders & Price Management

**Role:** Purchasing Officer, Admin.

This is the most detail-sensitive module in the demo — the purchase → FX → price chain is a real workflow the client specifically called out, not just a form.

### 6.1 Supplier Management (full CRUD)
**Screens:** Supplier List, Supplier Create/Edit, Supplier Detail (shows PO history for that supplier)
**Fields:** Name, contact person, phone/email, currency (default **USD**, since the client buys from 3rd-party suppliers in USD), payment terms, active/inactive status.

### 6.2 Purchase Orders
**Screens:** PO List (filterable by status/supplier), PO Create, PO Detail, Receive Stock (against an open PO)

**PO Create flow:**
1. Select Supplier
2. Add line items: Part, quantity, **unit cost in USD**
3. **Enter the FX rate applied to this purchase** (GHS per USD) — this is the actual rate paid, entered manually by the purchasing officer, not a live market feed
4. Save as Draft → mark as Sent

**Receive Stock flow:**
1. Open a Sent/Partially-Received PO
2. Enter quantity received per line (supports partial delivery)
3. On receipt: Inventory Balance increases, a Stock Movement is recorded, and **landed cost per unit is calculated** as `unit cost (USD) × FX rate recorded on the PO`

**[CONFIRMED]** One FX rate applies to the whole PO, and it is the rate used for every receipt against that PO — including partial and multiple deliveries. `fx_rate` therefore lives on the Purchase Order, not on the PO line and not on a payment record.

> Deferred, not dismissed: if the client later turns out to pay a supplier in installments at differing rates, that needs a rate-per-payment model, which changes the data model rather than just the UI. Out of scope for the demo — noted here so it isn't rediscovered as a surprise.

### 6.3 Price Management
**Screens:** Price List (all parts with cost, suggested price, final price), Price Edit

**Confirmed flow:**
1. Once a PO line is received, the system computes landed cost (6.2) and **auto-suggests a sell price**: `suggested price = landed cost ÷ (1 − margin% ÷ 100)`, where margin% is a configurable setting (global default for the demo — per-category override is a future refinement, not demo scope)

> **[CONFIRMED 17 September] margin% is a margin on the selling price, not a markup on cost** — 35% means 35% of what the customer pays. Whatever the admin sets in Settings is what gets suggested; the label and the formula agree, so the number does what it says.
2. Purchasing Officer/Admin reviews the suggested price and can **override it manually** — the final price is what gets saved
3. The **final price** (not the suggested price) is what the Sales role sees in POS (Section 3) — sales staff never see cost or suggested price, only the final sell price, consistent with RBAC

This is the one flow that touches four modules (Backoffice → IMS stock → Price Management → POS display) and is worth demoing as a single connected story: *receive a PO → see cost and suggested price appear → confirm the price → switch to the Sales login → see that exact price in POS.*

### 6.4 Currency handling — explicit, since it's easy to get wrong

**Purchase cost is in USD. Everything else — landed cost, suggested price, final price, and every price shown in POS — is in Ghanaian Cedis (GHS).** The only reason USD appears anywhere is that the supplier invoices in USD; the moment the FX rate is applied, the system is working entirely in Cedis from there on:

| Field | Currency | Why |
|---|---|---|
| `unit_cost_usd` on a PO line | **USD** | What the supplier actually charges |
| `fx_rate` on the PO | GHS per USD (a rate, not a currency amount) | The rate actually paid, recorded manually by the purchasing officer |
| `landed_cost` | **GHS** | `unit_cost_usd × fx_rate` — this conversion is what makes it GHS |
| `suggested_price` / `final_price` | **GHS** | Computed from landed cost, which is already in GHS |
| Price shown in POS | **GHS** | Sales staff never see USD anywhere — only the final Cedi price |

Worth being explicit about this in the database schema too — store `unit_cost_usd` and `fx_rate` as separate fields (never pre-convert and discard the original USD figure), so the actual purchase cost in USD is always recoverable for supplier reconciliation, even though every price-facing screen downstream displays GHS only.

## 7. Data Model Additions Needed for This Demo

Beyond the entities already defined in the Discovery Briefing (Part, Vehicle/Compatibility, Inventory Balance, Customer Account, Payment, Cheque, MoMo Transaction, Payment Allocation), this demo requires:

| Entity | Key fields | Currency |
|---|---|---|
| **Supplier** | name, contact, phone/email, currency, payment terms, active flag | USD (supplier's invoicing currency) |
| **Purchase Order** | supplier_id, status, order_date, fx_rate | fx_rate = GHS per USD |
| **Purchase Order Line** | po_id, part_id, qty_ordered, qty_received, unit_cost_usd | unit_cost_usd = **USD** |
| **Landed Cost** (computed, not necessarily stored) | = unit_cost_usd × fx_rate | **GHS** |
| **Price** | part_id, landed_cost, suggested_price, final_price, margin_pct_used | landed_cost, suggested_price, final_price = **GHS** |
| **User / Role** | email, password_hash, role (sales / purchasing / accountant / admin) | — |
| **Location** | name, active flag — one seeded row (`Main Shop`) for the demo; `location_id` is carried on Inventory Balance and Stock Movement but never surfaced in the UI (Section 4) | — |

## 8. Out of Scope for This Demo

Explicitly excluded to keep this buildable — these are real Phase 2+ items, not forgotten:

- Multi-location inventory — **confirmed single-location for the demo**: no location selector, no stock transfers. The schema is location-aware regardless (Section 4), so this is a UI/workflow exclusion, not a data-model one.
- Per-category or per-part margin overrides (single global margin% for the demo)
- Automated/live FX rate fetching (manual entry only, per client's stated requirement)
- Freight, duty, or other landed-cost components beyond unit cost × FX rate
- Full audit log UI (writes should still happen in the DB for good practice, but no dedicated audit log screen in the demo)
- E-commerce, SMS/WhatsApp notifications, reporting/BI dashboards beyond what's listed above
- Supplier payables / accounts payable (only receivables are in Financial Core scope here)
